## 对话驱动的品牌营销策略（2026-10-19 已上线）

用户通过同一工作空间制定品牌营销策略、补充约束和持续修改。每次有效结构化策略自动保存并回读核对，不增加人工审批、采用按钮或二次确认。比较版本用于理解变化，不是保存门槛。保留原有营销策略模型、版本记录、权限、幂等和冲突检测。保存策略不启动付费制作、广告投放或对外发布。

任务与会话分别持久化：会话按当前用户与品牌隔离，可以列出、恢复和继续；资料刷新不另起会话。历史来自已授权任务，不能把浏览器文本当作保存回执。较早消息通过游标分页查阅，支持按消息关键词查找会话；模型继续使用有界历史、阶段摘要及当前正式策略，不声称无限上下文。运行中允许停止及补充要求；补充以明确的后续任务处理，界面准确区分补充尚未生效与已生效，不能假装修改了正在生成的模型上下文。

进度来自授权任务状态及只含名称/状态的工具回执；支持流式的策略供应商可显示绑定当前任务路径与品牌的正文预览，明确标记尚未核对或保存。不返回原始工具参数、推理或未经确认的完成状态。任务完成后即使页面已关闭，由服务端完成处理执行策略自动保存；网络失败重试原操作，冲突保留原结果与当前正式版本并提示继续修改，不盲目覆盖。返回保存版本、时间、当前是否仍为该版本及变更摘要。

会话恢复完善（2026-10-19 已上线）：自动保存处于重试状态时，只读取原任务核对回执，不重新生成；读回成功后更新本轮保存状态。查阅更早消息不停止当前任务、不丢失未发送输入，并保持阅读位置；只有接近底部时新回复才自动跟随，离开底部可一键回到最新消息。当前阅读中已加载的消息不因新回复而裁剪，本机恢复缓存仍保留最近 40 条消息，模型历史预算保持不变。会话搜索采用最新请求结果，过期响应不得覆盖新搜索或切换后的会话。

成果连续性与回执（2026-10-19 已上线）：完成后的下一轮修改也关联同会话上一任务，服务端提供原成果及尚未保存的结构化方案，并以当前正式策略核对修改。每轮已核对的保存回执在聊天中显示版本、保存时间和实际变更章节；未知章节不展示技术字段，不把生成文本当作保存凭证。历史恢复沿用同样的回执展示，无审批操作。

Agent 工作台（2026-10-19 已上线）：聊天内可打开任务中心，查看本人当前品牌的任务、翻页、恢复会话及读取原结果；停止只操作选定任务，使用稳定操作键。运行详情显示已授权工具回执的名称与状态、固定 workspace 产物引用、实际加载的 Skill 摘要、账本 token 用量和待结算状态，不暴露工具参数、正文、推理或凭据。运行配置展示有效 Skill 安装状态及现有计量政策；全局 Skill 安装仍仅管理员通过原入口操作。新对话缺少必需 Skill 时在模型调用前拒绝，原已受理任务重试继续复用。工作偏好直接接入原修订校验编辑器；每轮读取用户当前偏好作为偏好而非事实或授权。用量计量不虚构余额、金额或硬额度。运行轮次、调用次数与执行时限由执行器和界面共用配置；偏好切换品牌时清除旧待提交操作并忽略迟到回执。

验收覆盖：同一品牌连续制定和修改、保存读回、并发冲突、丢回执重试、页面关闭后保存、跨设备恢复、不同品牌和用户隔离、补充/停止、320/390/768/1440布局。记录首个反馈耗时、完整任务成功率和恢复结果，模拟测试与真实模型/生产证据分开。

## `/BUG` 与 Platform AI 工程维护（2026-10-15，已上线并完成真实修复验收）

## 一、产品定位

**AMC-MM（AI Marketing Companion — Merchant Mode）** 是 AI Marketing Crew 为品牌主设计的移动端专属应用。

### 核心理念

> **"AI 员工，而非软件工具"**

品牌主不是在"使用一个 App"，而是在**与一名专属的 AI 营销员工对话**。这名员工了解品牌的菜单、语气、受众和历史内容，能够主动汇报工作状态，接受指令并执行操作。

### 与 AMC 主系统（工作人员端）的关系

| 维度 | AMC 主系统 | AMC-MM |
|------|-----------|--------|
| 目标用户 | 营销团队/代理 | 品牌主（餐饮老板等） |
| 操作深度 | 精细化管理 | 对话式指令 |
| 界面风格 | 看板/管理台 | 移动优先 AI 对话 |
| 使用频率 | 日常高频 | 碎片化/随时随地 |

---

## 二、用户画像

**典型用户**：连锁餐饮品牌主、独立餐厅老板  
**使用场景**：
- 在店内查看今日内容情况
- 出行途中语音指令 AI 生成内容
- 下班后快速审批 AI 准备好的帖子
- 随时了解品牌内容健康状态

**核心痛点**：
- 没有时间学习复杂的营销软件
- 需要随时知道"内容发没发、效果怎么样"
- 希望 AI 自动处理大部分事情，只在关键节点需要自己确认

---

## 三、设计原则

1. **AI 优先**：所有操作都可以通过对话触达，功能模块是对话的可视化辅助
2. **主动汇报**：AI 主动说话，不等用户问
3. **最少点击**：审批、确认类操作应在对话流中完成，无需跳转
4. **移动优先**：设计以手机竖屏为基准，所有交互适配拇指操作区

## 四、核心功能模块（按优先级排序）

---

### 🅰️ P0 — 功能 A：AI 查询（实时数据问答）

**描述**：AI 伴侣能够回答品牌主关于内容状态、发布记录的实时查询问题。

**支持的查询类型**：

| 用户说的话 | AI 需要调用的数据源 | 回答示例 |
|-----------|-----------------|---------|
| "今天排了几篇内容？" | `/api/dashboard/calendar` | "今天有 2 篇内容排期，分别是小红书下午 2 点和 Instagram 晚上 7 点。" |
| "小红书上次是什么时候发的？" | `/api/dashboard/brand-activity` | "小红书上次发布是 3 天前，已经有点久了，要我帮你写一篇吗？" |
| "有没有待我审核的草稿？" | `/api/brands/[id]/actions` | "有 2 篇草稿等待您确认，分别是周末特惠和新品介绍，我来念给您听吗？" |
| "这个月发了多少篇？" | `/api/dashboard/calendar` | "本月共发布了 12 篇内容，其中小红书 5 篇、Instagram 4 篇、Google 3 篇。" |

**技术要求**：
- AI 后端支持 **Tool-call 模式**（Function Calling）
- 定义查询工具函数：`get_calendar_events`、`get_action_items`、`get_brand_activity`
- AI 根据用户意图决定调用哪个工具，获取数据后以自然语言返回

**验收标准**：
- [ ] 用户问任何关于"今天/本周/上次"内容状态的问题，AI 能给出正确答案
- [ ] AI 在查询数据时不超过 3 秒响应
- [ ] 语音回答默认不超过 3 句话；文字策划按内容需要完整展开

### 🅳 P0 — 功能 D：主动开场白（Proactive AI Greeting）

**描述**：每次品牌主打开 AMC-MM，AI 伴侣**主动开口说话**，汇报当前最重要的工作状态，无需用户主动提问。

**开场白逻辑**（优先级检查顺序，取前 1-2 条拼成开场白）：

```
1. 🔴 有待审批草稿（ActionItems pending）
   → "老板好，有 X 篇内容准备好了等您确认。"

2. 🟡 品牌内容健康异常（某平台超过 3 天未发布）
   → "另外，[平台] 已经 X 天没更新了，要我帮您写一篇吗？"

3. 🟢 今日排期提醒
   → "今天 [时间] 有一篇 [平台] 内容将自动发布。"

4. ⚪ 无特别事项
   → "一切正常，今日暂无待处理事项。有什么需要我帮忙的吗？"
```

**个性化**：
- 开场白使用品牌名称
- 根据品牌 tone of voice 调整说话风格（正式/活泼）
- 时段感知：早上/下午/晚上使用不同问候语

**触发时机**：
- 页面首次加载时（每次打开 app）
- 用户在主界面停留超过 30 秒无操作时重新提醒

**技术要求**：
- 页面加载时并行调用：`/api/brands/[id]/actions`、`/api/dashboard/calendar`、`/api/dashboard/brand-activity`
- 将汇总数据作为 context 传给 AI，生成个性化开场白
- 自动触发 TTS（文字转语音）播报
- 头像同步进入"说话"表情状态

**验收标准**：
- [ ] 每次打开页面，AI 在 2 秒内开始说话
- [ ] 开场白准确反映当前实际数据状态
- [ ] 有待审批时，开场白必须提到
- [ ] 品牌超过 3 天未发布时，开场白必须提到

---

### 🅲 P1 — 功能 C：对话式草稿审核（Conversational Draft Approval）

**描述**：品牌主可以通过自然对话直接审批或拒绝 AI 生成的内容草稿，无需跳转到单独的审批页面。

**完整对话流程示例**：

```
AI（主动）: "老板，我给小红书写了一篇关于周末特惠的内容，您要听一下吗？"
用户: "说来听听。"
AI（读草稿）: "周末限定！波士顿大龙虾买一送一，仅限堂食。带上家人一起来，让每个周末都变得特别。📍[地址]"
用户: "发出去吧。"
AI（执行）: "好的！已安排在今天下午 6 点发布到小红书。"

---

用户: "重新写，改成更接地气的风格。"
AI（执行）: "收到！我来重新写一版..."
```

**支持的审核指令**：

| 用户意图 | 示例话术 | AI 执行的操作 |
|---------|---------|------------|
| 批准并发布 | "发出去"/"可以"/"就这样" | 调用 `/approve` API |
| 批准但调整时间 | "明天早上 10 点再发" | 更新 scheduledAt + approve |
| 拒绝重写 | "重新写"/"风格不对" | 调用重新生成 API |
| 拒绝并放弃 | "算了，先不发这篇" | 将草稿标记为 archived |

**多轮上下文记忆（架构要求）**：
- 前端维护 `conversationHistory[]`（用户/AI 交替消息记录）
- 每次请求将 history 传给后端 API
- 后端将 history 注入 prompt，AI 能理解"刚才那篇"指代哪个 draftId
- 当前活跃草稿的 draftId 通过 history 隐式传递

**验收标准**：
- [ ] 用户说"发出去"时，AI 能识别并调用正确的 draftId approve API
- [ ] 用户说"改成明天发"时，AI 能正确更新排期时间
- [ ] 用户说"重新写"时，AI 能重新生成内容（保留品牌上下文）
- [ ] 多轮对话中 AI 始终记住当前讨论的是哪篇草稿

### 7.6 用户认证与权限边界（Auth V2，当前有效）

AMC-MM 是品牌主与 BD 使用的客户端/BFF，`amc-kanban` 是身份、角色、品牌权限与工作日志的唯一权威来源。以下规则覆盖本文早期变更日志中“MM 本地重签 Session”“内部密钥跳过 ACL”“仅检查 Cookie 是否存在”等过渡方案。

#### 会话与登录

- 登录和注册由 `amc-kanban` 校验账号密码；AMC-MM 不保存密码，也不重新签发包含用户资料的 JWT。
- AMC-MM 原样接收并设置主系统签发的最小 Session Token。Token 只含 `sub`、`type`、`authVersion` 和标准 JWT 元数据，不缓存 email、role 或品牌权限。
- 新 Token 必须校验 `alg=HS256`、`iss=amc-kanban`、`aud=amc-users`、有效期和必要字段。
- 旧 `{ user: ... }` Session 只在明确配置的 1 天兼容窗口内接受；窗口结束后自动拒绝。
- 用户资料、显式角色和品牌列表从主系统 API 获取，不从 Session 动态推导。

#### 权限与代理

- `CrewMember` 是唯一直接品牌权限关系；组织成员仅通过组织 Owner 的 Crew 权限继承访问。
- AMC Agent 与人类用户使用同一套显式角色、Capability 和 Crew 权限；获得 ADMIN 后权限完全一致。
- AMC-MM 只转发 `Cookie`、`Authorization` 或 `x-api-key` 凭证，不接受或生成 `x-agent-id` 身份替换，也不转发浏览器提供的内部认证头。
- 品牌级 API 必须由 `amc-kanban` 完成 Capability + Crew 校验。AMC-MM 的本地 JWT 验证只可用于页面早期跳转，不能代替品牌授权。
- 素材 presign、confirm-upload 等写操作不得使用共享内部密钥绕过 ACL，也不得信任客户端注入的 `userId`；统一走主系统标准鉴权路径。

#### 本地服务端接口

- 所有会消耗付费资源、返回配置或访问业务数据的本地接口必须验证有效 Session，或直接代理到主系统完成认证。
- 禁止仅以“存在 session Cookie”作为认证成功条件。
- LLM/TTS/API 配置不得因主系统失败而向未认证浏览器降级暴露本地密钥。
- 代理目标固定为配置的 `amc-kanban` Origin；只转发必要请求头，并使用统一超时和错误响应。

#### 性能目标

- AMC-MM 本地 Token 校验不访问数据库，P95 < 5ms。
- 权限权威查询集中在主系统；单次品牌授权不再使用多条串行查询。
- 登录成功后不重复签名 Token；页面 bootstrap 中用户资料与品牌列表允许并行请求。

#### 验收标准

- [ ] 新 Session 可在 AMC-MM 与 `amc-kanban` 间原样互通，注销后本地域 Cookie 被清除。
- [ ] 伪造、过期、错误 issuer/audience 的 Cookie 均返回 401 或跳转登录。
- [ ] 无 Crew 权限用户不能通过 MM 的素材快速路径访问其他品牌。
- [ ] 本地 LLM/TTS/配置接口不存在“只有 Cookie 名就可调用”的路径。
- [ ] `typecheck`、生产构建、鉴权单元测试和 `/`、`/login`、`/dashboard` 冒烟测试全部通过。

## 十一、对话历史持久化方案（已决策）

### 策略：混合持久化

```
写入链路（每次对话结束后）：
用户发消息 → AI 回复 → 同步写入 localStorage → 异步写入 DB

读取链路（页面加载时）：
1. 优先读 localStorage（毫秒级，无 loading）
2. 后台静默 fetch DB 版本
3. 若 DB 版本更新（跨设备写入），合并并更新 localStorage
```

### 数据库 Schema（新增表）

```prisma
model CompanionMessage {
  id        String   @id @default(cuid())
  brandId   String
  userId    String
  role      String   // 'user' | 'assistant'
  content   String
  action    String?  // 记录 AI 执行了什么操作
  draftId   String?  // 关联的草稿 ID（审核场景）
  createdAt DateTime @default(now())

  brand     Brand    @relation(fields: [brandId], references: [id])
  @@index([brandId, userId])
  @@index([createdAt])
}
```

### 新增 API 端点

```
// 拉取历史记录
GET /api/brands/[id]/companion/history?limit=50
Response: { messages: CompanionMessage[] }

// 追加新消息（异步，非阻塞）
POST /api/brands/[id]/companion/history
Body: { role: 'user' | 'assistant', content: string, action?: string, draftId?: string }
```

### 前端实现细节

| 场景 | 行为 |
|------|------|
| 首次打开 | 从 DB 拉取最近 50 条，写入 localStorage |
| 对话中 | 立即写 localStorage，后台异步 POST 到 DB |
| 换设备打开 | DB 拉取，与本地 localStorage 合并（DB 优先）|
| 清除历史 | 清空 localStorage + 调用 DELETE API |

### 保留策略
- localStorage：保留最近 **100 条**消息
- 数据库：保留最近 **30 天**或 **500 条**（whichever comes first），超出自动归档

### v1.19 — 2026-07-01 · Feature & Bugfix: AI 伴侣 Azure Neural TTS 升级与 Greeting Autoplay 修复

**问题与需求**：
1. **自动播放 Greeting Message 失败**：在第一次加载页面或 brand 变化时，虽然 AI 伴侣能生成 Greeting 文本，但在首个用户手势交互（点击/触摸/按键）后无法触发播放，后台卡在 pendingSpeech 队列中。
2. **声音机械化**：本地 fallback 模式使用浏览器自带的 Web Speech API (`SpeechSynthesis`) 朗读，音质冰冷机械，极不自然。

**根本原因**：
1. **自动播放/Autoplay Mismatch**：`BrandOwnerDashboard.tsx` 与底层的 `useCompanionLive.ts` hook 重复定义了 `audioUnlockedRef` 和 `pendingSpeechRef`。用户手势交互仅解锁了 Dashboard 侧的状态，未能通知 hook 调用 `unlockAudio` 刷新 hook 内部的 speech 队列。同时，600ms 计时器运行后将 Dashboard 侧的 `pendingSpeechRef` 设为 null，使得后续手势调用被静默跳过。
2. **缺乏 SOTA Neural TTS 实现**：`useCompanionLive.ts` 中未引入 `microsoft-cognitiveservices-speech-sdk` 来请求高拟真的 Azure 神经网络语音（如 `zh-CN-XiaoxiaoNeural`），且 `BrandOwnerDashboard.tsx` 在流式响应时绕过 hook 独立使用了 native Web Speech 播报。

**修复方案**：
1. **统一 Unlock 状态与手势路由**：移除 `BrandOwnerDashboard.tsx` 里的所有重复 `audioUnlockedRef` 与 `pendingSpeechRef`，手势监听只调用 hook 的 `unlockAudio()`。Greeting Message 产生后直接同步调用 `speakText()`。
2. **引入 Azure Neural TTS**：
   - 在 `useCompanionLive.ts` 中集成 Azure SDK 动态加载与 token 代理机制。
   - 在 `useCompanionLive.ts` 中实现支持句子级别依次播报的内部队列机制（`ttsQueueRef` + `isSpeakingRef`），当没有流式 WebSocket 开启时，直接在本地以 Azure Neural TTS 形式渲染。
   - `BrandOwnerDashboard.tsx` 流式响应时不再使用本地 native SpeechSynthesizer，而是通过 `speakText(chunk, { queue: true })` 将句子压入统一的高音质队列播放。
   - 添加 `stopSpeaking()` 接口供 Dashboard 在新会话开始时清除上一轮播报。

**影响文件**：
- `src/components/companion/hooks/useCompanionLive.ts`
- `src/components/BrandOwnerDashboard.tsx`

### v1.5.1 — 2026-06-29 · Bugfix: Greeting TTS 播放两次

**问题**：每次进入 Dashboard，AI 伴侣的 Greeting 语音会重复播放两次。  
**根本原因**：`speakText()` 在浏览器 voices 未加载时进入 fallback 分支，同时注册了两个 resolve 路径：
- `window.speechSynthesis.onvoiceschanged` → 事件触发时调用 `pickAndSpeak()`
- `setTimeout(pickAndSpeak, 300)` → 300ms 后也无条件调用 `pickAndSpeak()`

当 voices 在 300ms 内加载完毕（大多数浏览器，尤其是第二次访问），两个路径均触发，`doSpeak()` 被调用两次，导致同一段语音被加入队列两次。

**修复**：引入 `voicesResolved` 布尔标志位，确保 `pickAndSpeak()` 只被调用一次，无论哪个路径先到达。

```ts
// 修复前（有竞争条件）
window.speechSynthesis.onvoiceschanged = () => { ... pickAndSpeak() }
setTimeout(pickAndSpeak, 300)  // ← 无论 onvoiceschanged 是否已经触发，始终执行

// 修复后（互斥保护）
let voicesResolved = false
const resolveVoices = () => {
  if (voicesResolved) return    // ← 只有第一个调用者能执行
  voicesResolved = true
  window.speechSynthesis.onvoiceschanged = null
  pickAndSpeak()
}
window.speechSynthesis.onvoiceschanged = resolveVoices
setTimeout(resolveVoices, 300)
```

**影响文件**：`src/components/BrandOwnerDashboard.tsx`

### v1.5.2 — 2026-06-29 · Bugfix: Greeting 仍然播放两次（深层根因修复）

**背景**：v1.5.1 修复了 `pickAndSpeak()` 的竞态条件，但 Greeting 仍然重复播放。

**根本原因（两个）**：

#### Bug A：`speakText()` audio 未 unlock 时，入队 + 继续执行 pickAndSpeak()
当 `audioUnlockedRef.current = false` 时，`speakText()` 会将文本放入 `pendingSpeechRef.current`（队列），但随后**继续**调用 `pickAndSpeak()`，尝试立即播放。这导致：
1. `pickAndSpeak()` 触发第一次播放（Chrome/Android 通常成功入队）
2. 用户 tap 后，`unlock()` handler 发现 `pendingSpeechRef.current` 非 null，再次调用 `speakText()` → **第二次播放**

**修复**：`speakText()` 在 audio 未 unlock 时，入队后立即 `return`，不再继续执行 `pickAndSpeak()`：
```ts
if (!audioUnlockedRef.current) {
  if (!pendingSpeechRef.current) pendingSpeechRef.current = cleanedText
  return  // ← unlock handler 会在手势回调中调用 speakText()
}
```

#### Bug B：`queryBrandId` sync effect 与 `loadInitialData` 重复调用 `setActiveBrand()`
当 URL 含有 `?brandId=xxx` 时：
1. `loadInitialData` 完成 → `setBrands(list)` + `setActiveBrand(found)` 
2. `brands` 状态更新触发 line 358 的 sync effect
3. 若 React batching 未将两次 setState 合并，该 effect 在 `activeBrand` 仍为 null 时执行，满足 `found.id !== null` → **再次调用 `setActiveBrand(found)`**
4. `activeBrand?.id` 变化 → `loadBrandDetails` effect 被再次触发 → **第二次 Greeting**

**修复**：引入 `initialLoadDoneRef` 标志，sync effect 首次执行时跳过（交由 `loadInitialData` 处理），后续 URL 变更时才接管：
```ts
const initialLoadDoneRef = useRef(false)
useEffect(() => {
  if (!initialLoadDoneRef.current) {
    initialLoadDoneRef.current = true
    return  // 首次加载由 loadInitialData 处理
  }
  // 后续 URL 变更才由此 effect 同步 activeBrand
  ...
}, [queryBrandId, brands])
```

### v1.21 — 2026-07-03 · Fix: OBS 素材直传签名 + 双重降级保障

**设计说明**：
- **OBS 签名匹配失败（403 SignatureDoesNotMatch）**：`getHuaweiObsPresignedPutUrl()` 将 `Content-Type` 纳入 AWS4 `SignedHeaders`。浏览器 `fetch` 在发送二进制 PUT 时可能对 `Content-Type` 做标准化处理（如添加 `; charset=utf-8`），与签名时的值不一致，导致 OBS 返回 403。
- **OBS PUT 失败无降级**：旧逻辑只在 presign 接口 502/504 时才降级，若 OBS PUT 本身失败（如 CORS 未配置），直接向用户报错无兜底。

**修复内容**：

**amc-kanban（`src/lib/integrations/huaweiObs.ts`）**：
- `getHuaweiObsPresignedPutUrl()`：`SignedHeaders` 从 `content-type;host` 改为仅 `host`
- 原则来源：file-storage-rules —「挥发性 Header（Content-Type）不得纳入 SignedHeaders」

**amc-mm（`src/components/BrandOwnerDashboard.tsx`）**：
- OBS PUT 失败时，对 ≤10MB 文件自动尝试服务端代理上传（原始 base64 路径）
- 全流程三步均加 `console.log` 输出，用户可通过浏览器 DevTools 定位失败步骤

**未解决风险**：
- OBS Bucket 的 CORS 策略需在华为云控制台配置，允许 `https://amc-mm.immedi.ai` 发起跨域 PUT 请求（`Access-Control-Allow-Origin`）。若未配置，浏览器直传会被 Preflight OPTIONS 拦截，此时会自动降级到服务端上传路径。

## User AI / API Key 同权契约（2026-10-01，权限底座已上线，完整验收进行中）
