# AMC Phase 1 Use Cases（基于 Phase 0 验收后的整理稿）

更新时间：2026-06-07
状态：Draft for Review

## 1. 目标与边界

Phase 1 目标：在 Phase 0 已完成能力上，打通“主理人邀请与品牌绑定 -> 品牌主入驻与建牌 -> Agent 接入与任务闭环 -> 看板可视化管理”的最小可运营闭环。

本稿遵循 Dify-first 原则：
- 工作流编排、知识库管理在 Dify 内完成。
- amc-kanban 负责权限、看板、审计、Agent 生命周期与上下文落地。

## 2. 角色定义（Phase 1）

1. AMC 主理人（Human Admin/Operator）
2. 品牌主（Brand Owner）
3. AMC Agent（AI Agent Worker）
4. AMC Research Agent（AI Agent Worker, 专项）
5. AMC Admin Agent（系统运维角色）

角色映射规则（已确认）：
- 现有与新增的 ADMIN 人类用户，默认同时视为 AMC 主理人。
- AMC 主理人身份不降级 ADMIN 权限；即同时具备主理人业务权限和系统管理权限。
- 非 ADMIN 的人类用户如需主理人能力，需后续通过角色扩展方案单独引入（不在 Phase 1 范围）。

## 3. Phase 1 In-Scope Use Cases

## 3.1 AMC 主理人

1. 邀请品牌主/代运营账号
- 通过邀请机制，由指定主账号（如 alextiannus@gmail.com）发起。
- 系统自动创建用户并生成邀请链接。

验收要点：
- 可追踪邀请发起人、被邀请人、过期时间、领取状态。
- 邀请可重发，旧链接自动失效。

2. 创建品牌并绑定品牌主
- 创建品牌时填写：品牌名、品牌主邮箱、可选联系方式。
- 若邮箱未注册，自动创建品牌主账号并完成品牌绑定。
- 支持品牌主添加协作者（多个 owner/collaborator）。

验收要点：
- 创建品牌成功后，品牌-品牌主绑定自动完成。
- 品牌主首次登录能看到已绑定品牌。
- 可在品牌内新增/移除协作者，并记录审计日志。

3. 修改和删除品牌
- 主理人可修改品牌基本信息。
- 删除品牌需要二次确认，并产生日志。

验收要点：
- 修改后看板和 API 查询结果一致。
- 删除遵循软删除或归档策略（需产品决策，见第 5 节）。

4. 创建 AMC Agent 序列并设置分配池
- 主理人可创建多个 AMC Agent，并加入可分配池。

验收要点：
- 可为 Agent 设置容量、优先级、路由标签（行业/地区）。
- 分配池变更有审计记录。

5. 修改/删除 AMC Agent（受绑定约束）
- 若 Agent 已绑定品牌，不允许物理删除；删除语义为软删除（INACTIVE/ARCHIVED），并支持迁移绑定关系。

验收要点：
- 已绑定 Agent 执行软删除后，不丢失历史任务和审计链路。
- 迁移后品牌任务归属与权限不丢失。

6. 使用 Agent Token 对接外部 AI Agent 应用
- 主理人可使用 AMC Agent Token 将外部 Agent 接入平台，成为 AMC 员工。

验收要点：
- Token 验证成功后可读写授权范围内资源。
- Token 轮换不影响审计链路。

7. 查看品牌列表与关键信息
- 可查看品牌列表、品牌 owner、连接中的 AMC Agent。

验收要点：
- 列表支持按 owner、agent、状态筛选。
- 明确显示当前主负责 Agent。

8. 通过看板查看 Agent 工作情况
- 主理人可通过看板查看任务进度、阻塞、完成情况。

验收要点：
- 至少支持 todo/in_progress/pending/done/void 状态可视化。
- 任务变更具备审计记录。

9. 与 AMC Agent 对话并沉淀品牌上下文
- 主理人与 Agent 对话，配置品牌设计、目标客户、品牌战略、平台策略、近期推广策略。

验收要点：
- 对话产出可沉淀到品牌上下文文档。
- Agent 在后续任务前会预读最新上下文。

## 3.2 品牌主

1. 邮箱注册（默认品牌主身份）
- 新用户注册默认身份为品牌主。
- 可填写联系方式、可选邀请码/reference code。

验收要点：
- 无 reference code 时按行业/地区路由优先分配，无法命中时回退到平台默认 Agent。
- 有 reference code 时优先绑定指定主理人的 Agent 池。

2. 自动分配 AMC Agent
- 品牌主注册成功后自动分配至少一个 AMC Agent（可扩展为多个协作 Agent）。
- 每个 Agent 默认可服务最多 30 个账号（可配置）。

验收要点：
- 分配策略可配置（容量上限、优先级、overflowPolicy、rebalancePolicy、行业/地区路由、默认兜底 Agent）。
- 分配失败有可观测错误并支持人工兜底。

3. 无品牌时进入欢迎页并引导建牌
- 登录后若无品牌，进入欢迎页并显示新增品牌入口。

验收要点：
- 欢迎语和 CTA 明确。
- 点击后进入“新品牌创建流程”。

4. 创建新品牌并选择计划
- 填写品牌名、选择运营计划、分配 Agent、同意服务协议并提交。

验收要点：
- 创建成功后自动完成品牌与当前品牌主绑定。
- 计划信息在品牌侧可查询。

5. 品牌创建后自动初始化 Workspace
- 自动生成品牌工作空间（brandcontext.md、素材库、内容库）。

验收要点：
- 首次创建品牌后，相关资源可见且可编辑。
- 初始化失败有重试机制或补偿任务。

6. 在品牌视角访问核心模块
- 可查看品牌看板、品牌报表、素材库、调研分享。

验收要点：
- 品牌切换后数据隔离正确。
- 权限边界明确（只能看到本人有权限品牌）。

7. 品牌信息完善（人机协作）
- Agent 协助完成品牌信息完善，品牌主也可手动配置。

验收要点：
- 人机修改均可审计。
- 冲突时以最近一次确认写入为准（或版本化，待决策）。

## 3.3 AMC Agent

1. Token 接入与初始化
- Agent 使用 Token 连接 amc-kanban，完成起名、介绍、头像设置。

验收要点：
- /agents/profile 初始化链路可用。
- 初始化完成后可执行授权任务。

2. 任务全量上板与状态闭环
- 品牌创建、信息修改、内容发布、策略讨论相关动作必须生成 Task 并追踪至 done/void。

验收要点：
- 关键动作都有任务卡片可追踪。
- pending 必须包含 requiredInput。

3. 品牌上下文持续更新与执行前预读
- Agent 将最新品牌理解写回上下文；执行策略讨论、内容创作、评论回复前预读上下文。

验收要点：
- 有明确“更新上下文”任务或日志。
- 预读失败时阻断执行并提示。

4. 多品牌切换上下文流程
- 切换品牌任务时，先更新旧品牌上下文，再清理会话上下文，再加载新品牌上下文。

验收要点：
- 切换流程可观察（日志/任务描述）。
- 不出现跨品牌上下文污染。

5. 主动发现并初始化新品牌
- Agent 可查询分配品牌列表，发现新品牌后主动执行初始化设置。

验收要点：
- 新增品牌在可控延迟内进入初始化队列。
- 初始化失败进入 pending 并请求必要输入。

6. 例行运营巡检
- 定时检查初始化进度、发布计划、内容排期、内容创作、评论回复。

验收要点：
- 具备固定巡检节奏和产出记录。
- 巡检异常自动生成告警任务。

7. 舆情和竞品信息更新
- 每日两次查看舆情，调整内容方向。
- 更新竞品信息到数据分析看板。

验收要点：
- 每日固定频次记录可查。
- 更新结果可关联到具体品牌和任务。

## 3.4 AMC Research Agent

1. 每日热点研究与同步
- 每日生成同城热点并同步到 amc-kanban。

验收要点：
- 输出结构标准化（来源、摘要、建议动作、适配品牌）。
- 输出可被内容任务直接引用。

## 3.5 AMC Admin Agent

1. 用户与品牌管理运维动作
- 修改用户密码。
- 创建新用户。
- 删除品牌。

验收要点：
- 全部动作需二次确认或强审计。
- 高风险动作具备可回滚策略（至少软删除）。

## 4. Phase 2 Deferred（已标注二期）

以下明确延后到 Phase 2：
1. 主理人通过品牌素材库管理品牌素材（完整能力）。
2. 主理人通过内容功能 review 草稿与配图（完整能力）。
3. 主理人通过素材库 AI 生图/视频能力生成素材。
4. Agent 记录并回写品牌级 Token 消耗。

说明：Phase 1 可先提供“可用但非完整”的基础能力，不作为二期完整验收项。

## 5. 关键约束（已确认）

0. 主理人身份约束
- 所有 ADMIN 用户默认归入 AMC 主理人角色池，无需额外开通。
- 主理人相关页面与接口在 Phase 1 以 ADMIN 为访问门槛。

1. 品牌 owner 关系约束
- 品牌支持多个 owner/collaborator，不强制单 owner。
- 约束：品牌至少有 1 个 owner；支持协作者增删与权限控制。

2. 品牌与 Agent 关系约束
- 品牌支持多个 Agent 协作，不强制唯一 lead Agent。
- 约束：需定义主负责 Agent 标识（用于默认通知与自动分配回填）。

3. 删除语义
- 品牌与 Agent 统一采用软删除（ARCHIVED/INACTIVE），保留审计与恢复能力。

4. Agent 自动分配策略
- 确认采用自动分配规则：capacity + priority + overflowPolicy + rebalancePolicy。
- Admin 用户可管理 Agent 分配池（启用/停用、容量、优先级、路由标签）。

5. 默认 AMC Agent 来源
- 无邀请码用户先按行业/地区路由分配；若无可用匹配，再回退到平台默认 Agent。

## 6. Phase 1 验收清单（建议）

1. 邀请注册闭环跑通（创建 -> 分享 -> 领取 -> 首次登录）。
2. 品牌创建闭环跑通（建牌 -> 绑定 owner/协作者 -> 分配 Agent -> 初始化 workspace）。
3. Agent 接入闭环跑通（Token 鉴权 -> 初始化 profile -> 可执行任务）。
4. 任务闭环跑通（todo -> in_progress -> pending -> done/void）。
5. 上下文闭环跑通（对话沉淀 -> 执行前预读 -> 切品牌不串上下文）。
6. 主理人视图跑通（品牌列表 + owner + agent + 工作看板）。
7. 高风险操作可审计（删品牌、删 Agent、改密码）。

## 7. 我对你这版 Use Case 的补充理解

1. 你要的不是“功能点集合”，而是“角色责任闭环”：主理人可配人配 Agent，品牌主可自助建牌，Agent 必须上板执行与可追踪交付。
2. 你强调了“组织治理”优先于“内容生产高级能力”：先把邀请、绑定、分配、上下文和任务流打稳，再做素材 AI 与内容生产增强。
3. 你把 Agent 视作真正员工，因此需要：身份名片、任务纪律、上下文纪律、巡检纪律、审计纪律。
4. 你已经预埋了二期增长点：素材库、草稿审核、AI 生图视频、Token 成本核算。

## 8. 建议的下一步讨论顺序

1. 确认第 6 节 7 条验收项是否作为 Phase 1 出口标准。

3. 将每条验收项拆成 API/前端/Dify workflow 三类开发任务。
