## 一、项目概述

### 1.1 项目背景
当前 AI Marketing Crew 系统在任务管理层面工作良好，但缺乏 **执行可追踪视角**：
- 无法快速回答"某 Agent 在某时间段做了什么"
- 无法量化"某项目在某时间段的实际进展"
- 无法分析"Human-AI 协作效率"
- 管理者复盘时只能手工拼表

### 1.2 项目目标
升级系统为一个 **执行追踪与分析平台**，使管理者能够：
1. 按主体（Agent/Human/Project）查看时间维度内的执行清单
2. 基于事件日志构建可信的指标体系
3. 自动生成周期复盘报告（周报、月报）
4. 识别延期与阻塞风险，支持主动管理决策

### 1.3 成功指标
1. 任意项目可在 60 秒内回答"上周完成了哪些工作、谁完成的、卡在哪"
2. 任意 Agent 可在 30 秒内查看"本周执行清单与完成率"
3. 周会可直接使用系统自动周报，无需额外人工拼表

## 三、查询模型

### 3.1 查询五维度
```
查询句式：在 [时间段] 内，[主体] 发生了哪些 [行为]，产生了哪些 [结果]？
```

| 维度 | 选项 |
|-----|------|
| **主体** | Agent / Human / Project / Business Flow |
| **时间** | 今天 / 昨天 / 近7天 / 近30天 / 自定义区间 / 自然周 |
| **行为** | 创建 / 分配 / 启动 / 进入等待 / 补充输入 / 完成 / 重开 / 返工 |
| **结果** | 已完成 / 进行中 / 等待输入 / 逾期 / 返工中 |
| **角色** | 主执行者 / Supportor / 创建者 |

### 3.2 关键概念定义

**执行行为**：
- 必须是有效推进动作，不包括纯查看或评论
- 例如：状态变更、内容更新、输入补充、分配变更

**完成**：
- 任务状态进入 `done` 的时刻
- 统计时按事件时间（不按创建时间）

**等待输入**：
- 任务处于 `pending/require_input` 状态的累计时长
- 计入项目延迟责任成本

**Supportor 介入**：
- Human 补充任务输入、解除阻塞、协助推进的行为
- 每次介入记录一条事件

## 四、指标字典（冻结版）

### 4.1 基础指标

| 指标 | 定义 | 公式 | 用途 |
|-----|------|------|------|
| 执行任务数 | 时间段内发生过有效推进的任务数 | COUNT(tasks with events) | 衡量活跃度 |
| 完成任务数 | 时间段内进入完成状态的任务数 | COUNT(tasks.status='done') | 衡量产出 |
| 完成率 | 完成任务占执行任务的比例 | 完成数 / 执行数 | 衡量效率 |
| 平均周期 | 完成任务平均耗时 | AVG(done_at - created_at) | 衡量速度 |
| 等待输入时长 | 任务处于等待状态的累计时长 | SUM(pending_duration) | 衡量阻塞 |
| Supportor 介入次 | Human 补充输入的次数 | COUNT(supporter events) | 衡量协作 |
| 权重贡献值 | 完成任务的权重之和 | SUM(weights of done tasks) | 衡量价值 |

### 4.2 衍生指标

| 指标 | 定义 | 用途 |
|-----|------|------|
| 项目推进度 | $\frac{\sum w_i(\text{done})}{\sum w_i(\text{all})}$ | Project 完成度 |
| 延迟责任占比 | 等待输入时长 / 总周期 | 归因分析 |
| 返工率 | 返工任务数 / 完成任务数 | 质量指标 |
| 人机交接成本 | 任务在 pending 状态经历的交接次数 | 协作效率 |

## 五、决策冻结（已锁定）

### 5.1 关键决策

| 决策项 | 选择 | 理由 |
|------|------|------|
| **Human 角色集合** | 仅 `supportor` | 简化上线，保留后续扩展空间 |
| **项目推进度** | 采用任务权重机制 | 避免简单计数偏差，体现任务价值 |
| **等待输入计责** | 是（计入项目延迟） | 风险可见，支持主动管理 |
| **报表时间窗口** | 自然周（周一-周日） | 对齐运营周期 |
| **MVP 首发视角** | Agent 优先 | 贴近当前运营动作 |

### 5.2 后续扩展预留

- Human 角色：预留 reviewer / owner / creator 等角色
- 权重机制：预留支持自定义权重规则
- AI 预测：预留预测延期、自动归因模块

## 七、Agent 周报模板（MVP 输出）

### 7.1 周报结构

**周报头部**
```

关联项目: [项目列表]
本周状态: [稳定 / 风险 / 异常]
```

**核心指标卡**
| 指标 | 数值 | 环比 |
|-----|------|------|
| 执行任务数 | 12 | ↑ +2 |
| 完成任务数 | 8 | ↑ +1 |
| 完成率 | 66.7% | ↓ -3% |
| 平均周期 | 2.5 天 | ↑ +0.2 天 |
| 等待输入时长 | 8 小时 | ↓ -2 小时 |
| Supportor 介入次 | 3 | → |

**完成清单**
| 任务名 | 项目 | 流程 | 权重 | 总耗时 | 等待时长 | Supportor 介入 |
|------|------|------|------|------|---------|----------------|
| [任务A] | [项目] | [流程] | 3 | 2 天 | 4h | 是 |
| [任务B] | [项目] | [流程] | 1 | 0.5 天 | 0h | 否 |

**风险清单**
- [任务 C]：高等待输入（>24h），需 Supportor 补充输入
- [任务 D]：2 次返工，质量风险
- [任务 E]：超时 1 天，需加速推进

**项目分布**
| 项目 | 完成数 | 权重贡献 | 推进度 |
|------|------|---------|------|
| [项目A] | 4 | 12 | 60% |
| [项目B] | 2 | 4 | 40% |
| [项目C] | 2 | 8 | 50% |

**本周总结**
- 本周执行 12 个任务，完成 8 个，完成率 66.7%
- 主要卡点在流程 B，等待输入 8 小时
- 项目 A 推进顺利，项目 B 需加速

**下周优先建议**
1. 等待输入：周一 10 点前补充任务 C 的决策
2. 加速推进：加急任务 D 的最终审核
3. 质量改进：任务 D 的返工原因，建议周会复盘

### 7.2 周报交互规则

- 任意指标卡可点击下钻到明细任务列表
- 完成清单表格支持按权重、耗时、Supportor 介入排序
- 风险清单支持按优先级筛选
- 导出为 PDF 或分享给关键干系人

## 十、数据与口径保障

### 10.1 事件模型（需新建表）

**任务事件表 (TaskEvent)**
```sql
CREATE TABLE TaskEvent (
  id STRING PRIMARY KEY,
  task_id STRING,
  event_type ENUM('created', 'started', 'pending', 'input_added', 'completed', 'reworked', 'reopened'),
  actor_id STRING,
  actor_type ENUM('AI_AGENT', 'HUMAN'),
  actor_role ENUM('executor', 'supporter', 'creator'),
  timestamp DATETIME,
  from_status STRING,
  to_status STRING,
  metadata JSON,
  created_at DATETIME
);
```

### 10.2 权重分级规则（暂定）

| 权重 | 任务特征 | 示例 |
|-----|---------|------|
| 1 分 | 低复杂度，单个 AI 独立完成 | 转发信息、数据整理、格式化 |
| 3 分 | 中复杂度，需 AI+Human 协作或多步骤 | 内容生成、投放优化、数据分析 |
| 5 分 | 高复杂度，跨流程或关键节点 | 项目规划、策略定稿、全流程审核 |

**规则**：产品定义权重，项目创建任务时选择权重，不允许任务运行中改权重。

### 10.3 时间口径

- **自然周**：UTC+8 时区，周一 00:00 - 周日 23:59:59
- **跨月周报**：支持自定义日期范围，但报表视图固定按自然周展示
- **事件时间**：精确到分钟，用于排序和汇总

### 10.4 数据准确性验证

**上线前验证**
- [ ] 对比 3 个历史周报与手工统计，误差 < 5%
- [ ] 验证权重总和与项目推进度算法
- [ ] 验证等待输入时长的计算（跨日期边界情况）

## 十一、风险与防护

### 11.1 风险清单

| 风险 | 影响 | 概率 | 防护 |
|-----|------|------|------|
| `supportor` 单角色不足 | 后续审计难区分角色 | 中 | 预留扩展位，后续可加 reviewer/owner |
| 权重主观性导致推进度失真 | 管理者不信任指标 | 中 | 先定义 3 档权重并固定，禁止动态改 |
| 等待输入计责引发争议 | 业务方反感 | 低 | 报表单独拆出"可控延迟"和"输入等待延迟" |
| 事件数据不完整 | 指标失真 | 中 | 在事件创建层增加数据校验，周报审核前手工验证 |
| 跨月时间算法错误 | 周报数据冲突 | 低 | 单元测试覆盖边界情况，上线前手工验证 |

### 11.2 防护措施

1. **权重锁定**：任务创建后权重不可改，避免追溯改数
2. **报表分段展示**：延迟责任分"可控"和"输入等待"两部分，便于理解
3. **数据审核卡点**：周报生成后需人工确认再发送，不自动推送
4. **渐进验证**：先 3 个 Agent 试用，数据对标无误再全量
