## 发现的问题与改进建议

### 🔴 高优先级

#### 1. MCP 配置路径问题
**现象：** Cowork 模式下，`claude_desktop_config.json` 是正确的 MCP 配置路径，但沙盒无法写入 `~/Library/Application Support/Claude/` 目录。  
**影响：** 每次新 Cowork session 都需要手动确认 MCP 已连接，无法在 session 内自动激活。  
**建议：**
- setup 脚本 `setup_amc_mcp.sh` 已就绪，用户需手动运行一次
- 考虑在 AMC Kanban 的 Agent 管理页面增加「复制 MCP 配置」按钮，方便用户粘贴到 claude_desktop_config.json

#### 2. MCP 工具中 `lark_notify` 仍作为默认通知机制
**现象：** `skills/agent-instructions.md` 中的 SYSTEM NOTICE 仍然要求 Agent 通过 Lark 创建文档草稿（"create a Lark doc draft"）。这与新的通讯架构（require_input 任务）冲突。  
**文件位置：** `src/lib/partner/mcp/server.ts` 第 20-31 行 `getSkillUpdateNotice()` 函数的 notice 文本  
**建议：** 更新 SYSTEM NOTICE，将 Lark doc 步骤替换为 `save_local_document` + `sync_to_kanban`

#### 3. `save_local_document` 依赖内部路由 dynamic import
**现象：** `save_local_document` 工具通过 `import('@/app/api/brands/[id]/documents/route')` 调用内部路由。这在 Next.js App Router 中可能导致 SSR/Edge runtime 不兼容问题。  
**建议：** 将核心逻辑提取为 service 函数，MCP 工具和 API 路由共同调用，避免循环依赖。

### 🟡 中优先级

#### 4. `get_brand_subscription` 返回格式
**需确认：** `GET /api/brands/[id]/subscription` 是否返回 `included_services` 字段（服务清单数组）。目前看到的路由可能只返回套餐基本信息（Tier 名称/价格），不包含具体服务细节。  
**建议：** 确保 subscription API 返回结构包含 `included_services: string[]`，让 Agent 可以动态解析工作范围，不依赖 hardcode。

#### 5. `get_platform_benchmarks` 数据源
**现象：** `GET /api/analytics/benchmarks` 已存在，但不确定是否有真实聚合数据（当前品牌数量可能不足以产生有意义的基准值）。  
**建议：** 冷启动阶段可以内置行业参考基准值（Ins 中餐类平均互动率约 3-5%，FB 约 1-3%），待品牌数量增长后替换为真实数据。

#### 6. Daily Memory 文件路径
**现象：** `write_daily_memory` 调用 `/api/brands/[id]/memory`，存储路径为 `fs` 本地文件。在 Render（无状态部署）环境下，本地文件系统重启后会丢失。  
**建议：** Daily memory 应存入数据库（Prisma），或使用 Render 的持久化存储（如 Huawei OBS，已集成）而非本地 `fs`。

### 🟢 低优先级

#### 7. Onboarding SYSTEM NOTICE 中的发布时段描述
**现象：** 现有 notice 提到"午餐/晚餐窗口"发布，但非餐厅品牌的最佳发布时段不同。  
**建议：** 发布窗口应从 brand subscription 的 `platform_coverage` 中动态获取，或由 Agent 根据历史数据自动选择。
